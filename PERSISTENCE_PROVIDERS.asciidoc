== Hibernate ORM

== Eclipselink

=== An `AttributeConverter` whose type arguments come from a generic superclass

EclipseLink applies a converter only if its class declares link:{persistence-api}/AttributeConverter.html[it].
A converter which inherits `AttributeConverter` from a generic superclass is dropped, without a warning.
The attribute is then mapped as if `@Convert` named no converter.
Measured in `oracle-sample-schemas-persistence` (`co`), with EclipseLink 5.0.2 and Hibernate ORM 7.4.12.Final.
The converter was `MappedShipment.ShipmentStatusConverter extends AttributeEnumConverter.OfString<ShipmentStatus>`.
`AttributeEnumConverter` is of `jinahya-persistence-more` 0.6.11-SNAPSHOT, and implements `AttributeConverter<E, A>`.
Under EclipseLink, reading the column value `IN-TRANSIT` failed with `EclipseLink-3002` (`ConversionException`).
The `DirectToFieldMapping` of `shipmentStatus` carried no converter, and took the string for a constant name.
Hibernate ORM resolved the type arguments through the superclass, and applied the converter.
The workaround redeclares the interface on the converter class, with its type arguments.
That is `ShipmentStatusConverter ... implements AttributeConverter<ShipmentStatus, String>`.
With it, the `co` unit tests and `Shipment_PersistenceIT` pass under both providers.
That EclipseLink reads the type arguments only from the class's own interfaces is inferred, not read in its source.

EclipseLink's source shows where it reads them.
`MetadataAsmFactory` keeps, for each class, the generic signature which the class itself declares.
That is its superclass and its interfaces, with their type arguments, flattened into one list of names.
`ConverterAccessor.initClassificationClasses` takes the last name of a converter's list as the column's type.
It takes the names before that one, from the third on, as the attribute's type.
It does not resolve `AttributeConverter<X, Y>` through the superclasses.
So the list ends in `Y` only when the converter's own `extends` or `implements` clause ends in it.
`implements AttributeConverter<ShipmentStatus, String>` makes it end in `String`, which is why the workaround works.
Read in the sources of EclipseLink 5.0.2 (`org.eclipse.persistence.jpa`).

Measured in `jinahya-persistence` (`more`), with EclipseLink 5.0.2 and Hibernate ORM 7.4.12.Final, against H2.
The converters were of `AttributeEnumConverter3`, a sketch in `jinahya-persistence-more` 0.6.11-SNAPSHOT.
It converts an enum, or an interface which more than one enum implements.
`OfSize extends AttributeEnumConverter3.OfString<_Size>` ends its list in the enum, `_Size`.
Writing `_Size.MEDIUM` failed with `EclipseLink-3002` (`ConversionException`).
The message was "The object [Medium], of class [class java.lang.String], (...) could not be converted to [class
(...)._Size]".
`OfISize extends AttributeEnumConverter3.OfString<_ISize<?>>` ends its list in the wildcard.
A class file's signature writes an unbounded wildcard as `*`.
Deploying the unit failed with `EclipseLink-7198` (`ValidationException`).
The message was "Class: [*] was not found while converting from class names to classes".
Declared as `OfISize extends AttributeEnumConverter3<_ISize<?>, String>`, its list ends in `String`.
The unit then deployed, and an entity with `null` in both attributes was stored and read back.
Hibernate ORM applied both converters, and `AttributeEnumConverter3_PersistenceTest` passes under it.
Under EclipseLink the test is skipped, by `assumeFalse(__PersistenceProviders.isEclipseLink(), ...)`.

=== Weaving

Without weaving, EclipseLink ignores `LAZY` on a basic attribute and on a to-one association (`@ManyToOne`,
`@OneToOne`).
It reads them at once, with the entity.
Woven, it honours `LAZY`, as Hibernate ORM does.
The specification allows either: `LAZY` is a hint, `EAGER` a requirement.
Weaving rewrites an entity's bytecode as the class is loaded, adding the code that reads an attribute when it is first
accessed.
The woven class implements `org.eclipse.persistence.internal.weaving.PersistenceWeaved`, and gains `_persistence_*`
fields.

==== An entity graph which names a basic attribute

EclipseLink applies an entity graph as a fetch group, given as `jakarta.persistence.fetchgraph`, as
`jakarta.persistence.loadgraph`, or to `find(EntityGraph, Object)`.
A fetch group needs the descriptor's fetch group manager, which EclipseLink has for a woven class only.
Unwoven, `find` with a graph naming a basic attribute fails with `EclipseLink-6114` (`QueryException`): "You must
define a fetch group manager at descriptor (...) in order to set a fetch group on the query".
Woven, the same `find` loads the attribute.
Hibernate ORM takes the graph either way; without bytecode enhancement it reads a lazy basic attribute at once.
Measured in `oracle-sample-schemas-persistence` (`co`), with EclipseLink 5.0.2 and Hibernate ORM 7.4.12.Final.
The graphs were the named ones of `Product` over the `@Lob @Basic(fetch = LAZY)` attributes `productDetails` and
`productImage`, in `Product_PersistenceIT.ProductDetailsTest` and `ProductImageTest`.
Unwoven EclipseLink skips those two tests.
Without a graph, `PersistenceUnitUtil.isLoaded(product, "productDetails")` after `find` is `false` under woven
EclipseLink, and `true` under unwoven EclipseLink and under Hibernate ORM without bytecode enhancement.
That is `ProductDetailsTest.__WithoutEntityGraph`.

==== How

Dynamic weaving, with no plugin.
The EclipseLink jar (`org.eclipse.persistence.jpa`) is itself a Java agent (its `Premain-Class` is
`JavaSECMPInitializerAgent`), handed to the test JVM on the `argLine`.
`oracle-sample-schemas-persistence` does it with a profile, in its root `pom.xml`, beside the provider profiles:

[source,xml]
----
<profile>
  <id>jakarta-ee-11-eclipselink-weaving</id>
  <properties>
    <argLine>-javaagent:${settings.localRepository}/org/eclipse/persistence/org.eclipse.persistence.jpa/${version.org.eclipse.persistence}/org.eclipse.persistence.jpa-${version.org.eclipse.persistence}.jar</argLine>
    <eclipselink.woven>true</eclipselink.woven>
  </properties>
</profile>
----

`version.org.eclipse.persistence` is the project's EclipseLink version property (`5.0.2`).
surefire and failsafe read `argLine` by default, and `jacoco:prepare-agent` adds its own agent to the same property, so
both agents run.
`eclipselink.woven` defaults to `false` in `<properties>`, and surefire and failsafe pass it to the tests in
`<systemPropertyVariables>`, so a test can tell a woven run.

The profile is an add-on, not a provider.
Named alone, it hands the agent to a JVM with no EclipseLink to run it, so it is named with the provider profile:

[source,shell]
----
./mvnw -Pjakarta-ee-11-eclipselink,jakarta-ee-11-eclipselink-weaving clean test
----

Adding `failsafe` to the profiles runs the `*_PersistenceIT` classes woven too, against the database.
Nothing on disk is rewritten: the classes under `target/` and the packaged jars stay unwoven, whichever profiles built
them.
`eclipselink.weaving` stays unset in `persistence.xml`, where it is commented out in both units.
The default build stays unwoven.

`jinahya-persistence` has the same profile, and the same `eclipselink.woven` property, in its root `pom.xml`.

==== Checking a class is woven

`__Object_Test.isWovenByEclipseLink(Class)` walks the class and its superclasses for an interface named
`org.eclipse.persistence.internal.weaving.PersistenceWeaved`.
It matches by name, so it compiles, and answers `false`, without EclipseLink on the class path.
Each of the three schema modules of `oracle-sample-schemas-persistence` has one in its `__Object_Test`.

`jinahya-persistence` has one in `__PersistenceProviders`, beside `isEclipseLink()`.
`isEclipseLink()` tells whether `org.eclipse.persistence.jpa.PersistenceProvider` is on the class path.
It looks the class up by its name, without initializing it, so it compiles without EclipseLink too.
The class is in `src/test-shared/java` at the root of `jinahya-persistence`.
`build-helper-maven-plugin` adds that directory to the test sources of every module, which each compile it.

==== What a woven run skips

`__Object_Test.equals_verify_` skips a woven class, an entity or an embeddable, and so does `co`'s
`Naive_Customer_Test.equals_verify`.
Woven, `equals` reads getters which EclipseLink rewrote, and EqualsVerifier fails on the instances it builds: "equals
throws MockitoException when field orderTotal is null", for `co`'s `CustomerOrderProduct`.
The unwoven runs verify the same methods.
Measured in `oracle-sample-schemas-persistence`, with EclipseLink 5.0.2: woven, the unit tests (`co` 154, `hr` 150,
`sh` 351) and the ITs (`co` 114, `hr` 49, `sh` 64) pass, with those skips.

`postgresql-demodb-persistence` had the same profile from `f368f4b` until it dropped EclipseLink in `3b6b91b`.
There, woven, EclipseLink 5.0.2 failed inside `getReference` for an entity whose identifier is an `@EmbeddedId`
(`RouteId`), with a `NullPointerException` at `ObjectBuilder.buildAttributesIntoShallowObject`.
The unwoven runs, and Hibernate ORM, passed the same tests.

==== Static weaving

Not used.
`staticweave-maven-plugin` (`de.empulse.eclipselink`, `1.0.0`) is declared in the `<pluginManagement>` of
`oracle-sample-schemas-persistence` and of `mysql-sakila-persistence`, and bound in neither.
Static weaving would rewrite the classes at build time, and the jars would ship woven.
