= submodule_release

Releases one submodule under `projects/`, and later deploys it to Maven Central. The two are separate:

* *Release* makes the tag `x.y.z` and pushes `main`, `develop` and the tag. Nothing goes to Central.
* *Deploy* uploads the tag to Central, any time later, once what it depends on is there.

When the submodules share a unified version, the book's repository gets that version as a tag too ("Book tag"); it is
never deployed.

== Layout

`projects/` is itself a submodule, `jakarta-persistence-applied-book-projects`, the repository readers clone. It holds
the submodules, over HTTPS, following `develop`. So a pointer moves at two levels: a submodule's new commit is
committed in `projects/`, and `projects/`'s new commit in the book's repository ("Book pointers").

Pushing from inside the HTTPS submodules goes over SSH through `pushInsteadOf`, set once on the machine:

[source,sh]
----
git config --global url."git@github.com:jinahya/".pushInsteadOf "https://github.com/jinahya/"
----

== JDK

Every Maven command here runs on JDK 25, the projects' baseline: each module, and the book's repository, has `jenv local 25`
(a `.java-version`, git-ignored in the submodules), and through each module's own `./mvnw` (Maven 3.9.16), never a
system `mvn`: Maven 3.10.0 stages a Central bundle with local-repository files (`maven-metadata-local.xml`,
`_remote.repositories`), which Central rejects. Check that `./mvnw -v` says 25 before a run; a newer JDK fails
tests that pass on 25 (EqualsVerifier 4.5.2 on JDK 27, for one).

== Parent

Every submodule has `io.github.jinahya:jinahya-parent` as its parent, all at the same, latest released version. Its
`maven-release-plugin` configuration is what the steps below rely on:

[source,xml]
----
<tagNameFormat>@{project.version}</tagNameFormat>
<autoVersionSubmodules>true</autoVersionSubmodules>
<pushChanges>false</pushChanges>
<localCheckout>true</localCheckout>
<goals>install</goals>
<arguments>-DskipITs</arguments>
----

* `tagNameFormat`: the tag is the bare version, `x.y.z`.
* `pushChanges` `false`: `release:prepare` pushes nothing; Release step 7 does.
* `goals` `install`: `release:perform` installs `x.y.z` into `~/.m2/repository` but does not deploy; Deploy does.

== Dependencies

The submodules are git submodules, not Maven modules: no aggregator `pom.xml` builds them together, and one depends
on another only through a released version in its `pom.xml`. For the submodule at hand, find:

* what it depends on: between releases, a dependent's `develop` uses the sibling's `-SNAPSHOT`, the version on the
  sibling's `develop` (e.g. `postgresql-demodb-persistence` on `jinahya-persistence` `0.6.11-SNAPSHOT`), never a
  released version; only at release does it use the sibling's released version, never a `-SNAPSHOT`, and right after
  its own release it goes back to the sibling's new `-SNAPSHOT` (see "Order");
* what depends on it: the siblings that move to its new version after the release.

To find them, grep every submodule's `pom.xml` for the `io.github.jinahya` artifacts the others publish.

`projects/README.md` lists the same dependencies, artifact and scope without versions, under "Inter-dependencies".
When a submodule's `pom.xml` gains or drops a sibling artifact, or changes its scope, update that table and the table
below together. A version change alone leaves the README as it is.

== Order

. *Verify all, once, before any release.* Not per submodule, but once before them all: in each submodule, on its
  `develop`, commit any uncommitted work (never stash or discard it), align the versions (see "Book tag"), set each
  dependent's sibling version to the `-SNAPSHOT` on that sibling's `develop` ("Dependencies"), and
  check, before committing the alignment, that it installs and its site builds, in dependency order, so a dependent
  resolves what its dependency just installed:
+
[source,sh]
----
./mvnw clean install site
----
+
If it fails, or reports something that needs fixing, fix whatever is required and run it again until it passes. Then
commit the alignment and the fixes on `develop`, so every submodule's `develop` is committed and clean, as Release
step 1 requires.
. *Release all, in dependency order.* A submodule is released only after everything it depends on. When a dependency
  is released, move each dependent to `x.y.z` in a commit of its own on its `develop`, then release the dependent.
  This is where a dependent that used the sibling's `x.y.z-SNAPSHOT` ("Dependencies") takes its release; one that
  used a `-SNAPSHOT` of a sibling not being released stops here, and is reported.
  The dependent builds against the `x.y.z` the release installed into `~/.m2/repository`, so it never waits on
  Central. Once the dependent is released (Release step 7 pushed), move it back, on its `develop`, to the
  dependency's `<next>-SNAPSHOT`, the version now on the dependency's `develop`, in a commit of its own, and push
  `develop`. `release:perform` installs only `x.y.z`, so first install the dependency's `<next>-SNAPSHOT`, once,
  from its `develop` (`./mvnw clean install`), and check that the dependent builds against it (`./mvnw clean install`)
  before committing; so between releases it uses the sibling's snapshot again ("Dependencies"), and `projects/` and the book
  take the new pointer ("Book pointers").
. *Deploy later, one by one, in the same order.* A submodule is deployed only when every sibling artifact it depends
  on is actually on Central (Deploy step 1), so that whenever a dependent resolves from Central, what it needs does
  too.

As of 2026-10-30:

. `jinahya-persistence`: others depend on it, so it goes first.
. `mysql-sakila-persistence` and `postgresql-demodb-persistence`: after their `version.jinahya-persistence` moves to
  the version just released; they do not depend on each other, so either goes first.
. `heads-of-governments-persistence`: depends on nothing, so any time, but before the `-data` modules, which depend
  on it.
. `heads-of-governments-jakarta-data` and `heads-of-governments-spring-data`: after their
  `version.heads-of-governments-persistence` moves to the version just released; they do not depend on each other,
  so either goes first. Released only, never deployed.

== Release

. *Precondition.* The submodule is on the `develop` branch with a clean git status (nothing modified, staged or
  untracked), and its `pom.xml` uses no sibling artifact at a `-SNAPSHOT` version; `projects/` is on its `develop`
  with a clean git status too; and `git remote -v`, in the submodule, shows an SSH URL for `(push)` (see "Layout").
  If any of these does not hold, stop and report it; do not go on.
. *Release branch.* Take the project version from the submodule's root `pom.xml`, which is `x.y.z-SNAPSHOT`, drop
  the `-SNAPSHOT` suffix, and switch to a new branch `release/x.y.z` from `develop` (e.g. `0.6.8-SNAPSHOT` →
  `release/0.6.8`).
. *Release.* On `release/x.y.z`, run
+
[source,sh]
----
./mvnw release:prepare release:perform -DreleaseVersion=x.y.z -DdevelopmentVersion=<next>-SNAPSHOT
----
+
The values of `-DreleaseVersion` and `-DdevelopmentVersion` are provided by the author; if they are not given, ask
for them before running. When it is done, `release/x.y.z` has two new commits and one new tag:
+
--
* the commit that sets the version to `x.y.z`, which the tag points at;
* the commit that sets the version to `<next>-SNAPSHOT`;
* the tag `x.y.z`.
--
. *Main.* Switch to `main` and merge the first of those two commits, the one with the non-snapshot version `x.y.z`:
+
[source,sh]
----
git switch main
git merge release/x.y.z~1
----
. *Develop.* Switch to `develop` and merge the whole release branch, which ends with the `<next>-SNAPSHOT` version:
+
[source,sh]
----
git switch develop
git merge release/x.y.z
----
+
Steps 4 and 5 together are how the two branches keep their roles: `main` always holds the latest released,
non-snapshot version, and `develop` always holds the new snapshot version.
. *Cleanup.* Delete the release branch:
+
[source,sh]
----
git branch -d release/x.y.z
----
. *Push.* Push `main`, `develop` and the tag:
+
[source,sh]
----
git push origin main develop x.y.z
----
. *Book.* In `projects/`, on its `develop`, commit the submodule's new commit (the tip of its `develop`) and push
  it; then, in the book's repository, on its `develop`, commit `projects/`'s new commit:
+
[source,sh]
----
cd projects
git add <submodule>
git commit -m "Point at <submodule> x.y.z"
git push origin develop
cd ..
git add projects
git commit -m "Point at <submodule> x.y.z"
----

== Deploy

Per submodule, any time after its release, one by one in the order above, except the `-data` modules,
`heads-of-governments-jakarta-data` and `heads-of-governments-spring-data`: they are released, tagged and pushed like
the others, but never deployed to Central.

. *Dependencies on Central.* For every sibling artifact the tag's `pom.xml` depends on (see "Dependencies"), check
  that its version is actually on Central, i.e. its `.pom` answers `200`:
+
[source,sh]
----
curl -s -o /dev/null -w '%{http_code}\n' \
  https://repo1.maven.org/maven2/io/github/jinahya/<artifactId>/<version>/<artifactId>-<version>.pom
----
+
If any is not there yet, stop and report it; deploy later.
. *Deploy.* From `develop`, check out the tag `x.y.z` (detached), deploy it to Maven Central, and switch back to
  `develop`:
+
[source,sh]
----
git switch -d x.y.z
./mvnw -Pcentral clean deploy && git switch -
----

== Book pointers

`projects/` keeps every submodule at the tip of the submodule's `develop`, its snapshot, never at a release tag or at
`main`, and the book's repository keeps `projects/` at the tip of its `develop`. Whenever a submodule's `develop` moves
(Release step 8, a dependent moving to a new version, a fix from "Verify all"), `projects/` commits the new pointer on
its `develop` and pushes it, and the book commits `projects/`'s new pointer on its own `develop`.

== Book tag

From now on the submodules may share one, unified version. When they are all released at that version `x.y.z`, this
repository itself is tagged `x.y.z` as well, on its `develop` commit that points at those releases (Release step 8).
So is `projects/`, first, on its `develop` commit that points at them; it has no `pom.xml`, so the tag is all it
gets. That tag is what readers clone the book's version by
(`git clone --branch x.y.z --recurse-submodules ...`):

[source,sh]
----
cd projects
git tag x.y.z
git push origin x.y.z
cd ..
----

This repository is a Maven project (`com.github.jinahya:jakarta-persistence-applied-book`), but it is a book: it is never deployed to Central, so it has a tag but no Deploy. It has no parent
either, not `jinahya-parent` nor any other, so none of the `maven-release-plugin` configuration under "Parent"
applies to it.

The book's version follows the submodules', by hand, since it has no release plugin and no `main`: on this
repository's `develop`, after the commit that points at the released submodules,

. set the `pom.xml` version to `x.y.z` and commit it; the tag `x.y.z`, a plain git tag named the same as the
  submodules', goes on this commit;
. set the `pom.xml` version to `<next>-SNAPSHOT` and commit it;
. push `develop` and the tag.

[source,sh]
----
./mvnw -q versions:set -DnewVersion=x.y.z -DgenerateBackupPoms=false
git commit -am "Release x.y.z"
git tag x.y.z
./mvnw -q versions:set -DnewVersion=<next>-SNAPSHOT -DgenerateBackupPoms=false
git commit -am "Prepare for <next>-SNAPSHOT"
git push origin develop x.y.z
----

The unified version is `jinahya-persistence`'s: it already has released versions (`0.6.5`, `0.6.6`, `0.6.7`, ...),
so every other submodule, and the book's repository, aligns to its line rather than the other way round.

As of 2026-10-26, the four submodules then (`heads-of-governments-persistence`, `jinahya-persistence`,
`mysql-sakila-persistence`, `postgresql-demodb-persistence`) and the book's repository are released at `0.6.9` (each tagged
`0.6.9`, not yet deployed), and their `develop` is at `0.6.10-SNAPSHOT`. The `-data` modules, added on 2026-10-29,
start at `0.6.10-SNAPSHOT` and have no release yet.
