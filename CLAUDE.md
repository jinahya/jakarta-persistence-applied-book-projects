# CLAUDE.md

Guidance for working in `projects/`, the repository `jakarta-persistence-applied-book-projects`, which is itself a git
submodule of the book's repository. Every project here is a git submodule of its own; see `README.md` for the list.

The book's `../CLAUDE.md` delegates everything about the projects to this file; its own rules (the manuscript, disk
truth of code blocks, never reverting uncommitted work destructively, checking for running skills or loops first) still
hold here. A project's own `CLAUDE.md` wins over this file for that project.

## Absolute rules

- **A project runs on both providers, or on Hibernate ORM only, by its database.** Some databases are not easy to work
  with on EclipseLink, so their projects target Hibernate ORM only; see [Providers](#providers). Never add EclipseLink to
  a Hibernate-ORM-only project, or drop it from a project of both, without the author.
- **`postgresql-demodb-persistence` keeps its entities in `src/test/java`.** `src/main/java` holds the mapped
  superclasses (`mapped/`) only. It has the two units, `test` on H2 in PostgreSQL mode and `it` on the demo database;
  see that module's `CLAUDE.md`.
- **Unsure, broad, mechanical changes across several projects are asked first.** Check the change against disk and the
  conventions below, and ask the author when it is not clear.

## Building

Each project builds on its own, with its own wrapper, from its own directory, on Java 25. A project may depend on a
`-SNAPSHOT` of another one here; install that first (`./mvnw install -DskipTests` in `jinahya-persistence`, say).

- `./mvnw test-compile` compiles every test without a database.
- `*_PersistenceTest` runs under surefire, on the `test` unit.
- `*_PersistenceIT` runs under failsafe, only with `-Pfailsafe`, on the `it` unit, against the installed database.

Persistence units are named `test` and `it`; a module of several schemas or databases prefixes them (`hr-test`,
`adventureworks-it`). `heads-of-governments-persistence`, on SQLite, has `test` only.

## Providers

The provider is the `persistence-unit.provider` property, which `persistence.xml` reads; a profile per provider sets
it.

| Project | Providers | Profiles |
|---|---|---|
| `heads-of-governments-persistence` | Hibernate ORM | none; `persistence.xml` names it |
| `mysql-sakila-persistence` | Hibernate ORM and EclipseLink | `jakartaee-11-hibernate-orm`, `jakartaee-11-eclipselink` (`-weaving`) |
| `oracle-sample-schemas-persistence` | Hibernate ORM and EclipseLink | `jakartaee-11-hibernate-orm`, `jakartaee-11-eclipselink` (`-weaving`) |
| `postgresql-demodb-persistence` | Hibernate ORM only | none; the property's default |
| `sqlserver-samples-persistence` | Hibernate ORM only | none; the property's default |

- **Both providers:** a mapping keeps to Jakarta Persistence, and runs, with its tests, on each profile. Where the two
  differ, the code works on both and says so in a comment or the javadoc (`insertable = true` on an `@Id` for
  EclipseLink, `@Enumerated(STRING)` beside `@EnumeratedValue` for Hibernate ORM, say).
- **Hibernate ORM only:** the database is not easy to work with on EclipseLink. Hibernate ORM's own features are
  welcome where Jakarta Persistence falls short; say in the javadoc where a mapping is Hibernate ORM's.

## `src/test/sql`: profiling queries

A file per scope; the module is the scope a query can join within (a schema in SQL Server or PostgreSQL is a namespace,
not a join boundary):

| Scope | File |
|---|---|
| the module as a whole (the database, or Oracle's schema) | `__.sql` |
| one schema, in a module of several schemas | `_<Schema>.sql`, in the schema's own case |
| one table or view | `<table>.sql`, in the database's own case; `<Schema>_<Object>.sql` in SQL Server |

SQL Server keeps the schema prefix because object names repeat across schemas (`Sales.Customers`,
`Website.Customers`).

## `src/test/sql-exercises`: the exercises

```
src/test/sql-exercises/
├── EXERCISES.asciidoc     every problem, under [[<ID>]]
├── EXERCISES.yaml         the registry: id, section, tier, title, sql, test, native-only, retired
├── __/                    the whole module
├── <table>/               one table or view
└── _<Schema>/             one schema (SQL Server)
    ├── 01_basic.sql
    ├── 02_intermediate.sql
    └── 03_advanced.sql
```

- A directory is named after the file of `src/test/sql` it exercises, case and all (`actor/`, `EMPLOYEES/`,
  `_HumanResources/`, `__/`).
- A file holds its level's exercises in id order, each under a ruler that carries its id. A level with no exercise has
  no file.
- Ids are permanent; see the header of each `EXERCISES.yaml`. `../PROJECTS_EXERCISES.asciidoc`, in the book, picks the
  exercises the book shows.
- Exercise SQL pages in the optimal form the database permits (`LIMIT n`, `OFFSET m` only past the first page;
  `setMaxResults` / `setFirstResult` likewise), as the book's `../CLAUDE.md` states it.

## `src/test/java-exercises`: the tests of the exercises

`src/test/java` keeps to the persistence tests. The tests that answer the exercises are in `src/test/java-exercises`,
which each project's root `pom.xml` adds as a test source with `build-helper-maven-plugin` (execution
`add-exercises-test-source`), in no profile.

- A class per live exercise, `<ID>_PersistenceIT`, with `@DisplayName("<ID>: <title>")`, in a subpackage of the
  module's test package made of the id's parts before the level, lowercased, underscores kept: `SAKILA_ADDRESS_A_02`
  → `….persistence.sakila.address.SAKILA_ADDRESS_A_02_PersistenceIT`, `SAKILA_ACTOR_INFO_B_01` → `sakila.actor_info`,
  `AW_HUMANRESOURCES_I_01` → `aw.humanresources`. A retired id has no class.
- Every exercise class is an IT, run by failsafe (`-Pfailsafe`), whatever the database; the SQLite module's run on its
  `test` unit.
- The class of an exercise the module's `EXERCISES_PICKS.asciidoc` picks answers it, with `__QueryLanguage` and
  `__CriteriaApi` (or `nativeQuery` where neither can); any other class is empty.
- The registry's `test:` names the class relative to the module's test package (`sakila.address.SAKILA_ADDRESS_A_02_PersistenceIT`).
- Helpers the classes share are in a public `__Exercises_TestUtils` in the module's test package; the classes, in
  other packages, reach the entities through their public members only.
- `src/test/java-exercises` may use anything in `src/test/java`; `src/test/java` never uses `src/test/java-exercises`.

## Java code

- **`Optional` over the ternary operator for a null-safe value.** Write
  `Optional.ofNullable(category).map(Category::getCategoryId).orElse(null)`, not
  `category == null ? null : category.getCategoryId()`.
- **A provider's own types are written fully qualified, never imported.** In every `*-persistence` project, in
  `src/main/java`, `src/test/java` and every `src/test/java-*`, a type of Hibernate ORM (`org.hibernate.*`), EclipseLink
  (`org.eclipse.persistence.*`) or an extension of theirs (Hibernate Spatial, geolatte `org.geolatte.*`) is written with
  its package at each use, `@org.hibernate.annotations.JdbcTypeCode(org.hibernate.type.SqlTypes.ARRAY)`, so that a
  reader sees at once where a mapping or a test leaves Jakarta Persistence. `jakarta.*` types are imported as usual. The
  book's `[source,java]` blocks quote these lines as they are.

## Shared files

- **The projects share one `.gitignore` and one `.idea/codeStyles`.** Every submodule here (and under `data/`) has the
  same `.gitignore`, which ignores `.idea/*` but keeps `!.idea/codeStyles/`; what a single project needs goes at its
  end, under "This project". Every submodule but `jinahya-persistence` tracks the same plain
  `.idea/codeStyles/Project.xml` and `codeStyleConfig.xml`.
- **`jinahya-persistence` is the exception, and we don't touch it:** its `.idea/codeStyles` is a git submodule
  (`onacit/dot-idea-codestyles`), with its own content; never replace it with plain files, copy it to the others, or
  bump it.
