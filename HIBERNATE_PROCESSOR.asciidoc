= Primary entity type and a generic intermediate repository

Why each Jakarta Data repository of `heads-of-governments-jakarta-data` names `CrudRepository` with its own types,
next to the module's generic base `_Repository<T, U>`, as the module's `README.md` records it.
Jakarta Data 1.0.1; hibernate-processor 7.4.13.Final (unchanged on `main` and in 8.0.0.Beta4).

== Symptom

The repositories share a generic base, which is not annotated `@Repository`, so nothing is generated for it:

[source,java]
----
interface _Repository<T, U>
        extends jakarta.data.repository.BasicRepository<T, U> {
    ...
}
----

A repository that extends only the base does not build, whether the base extends `BasicRepository<T, U>` or
`CrudRepository<T, U>`:

[source,java]
----
@Repository
public interface HeadRepository
        extends _Repository<Head, Long> {
----

....
HeadRepository.java:[18,8] repository does not have a well-defined primary entity type for inherited member 'deleteById'
....

== What the specification says

The inherited `save`, `deleteById`, `findById`, and so on need the repository's _primary entity type_.

Jakarta Data 1.0.1, the version the module uses
(https://github.com/jakartaee/data/blob/1.0.1/spec/src/main/asciidoc/repository.asciidoc), says how a repository
declares it:

[quote]
Users of Jakarta Data declare a primary entity type for a repository by inheriting from a built-in repository super
interface, such as `BasicRepository`, and specifying the primary entity type as the first type variable.

It does not say whether a built-in supertype inherited through a generic interface of one's own, as
`BasicRepository<T, U>` through `_Repository<Head, Long>`, counts.

Jakarta Data 1.1 says it does not. Since 1.1.0-M4, its specification
(https://github.com/jakartaee/data/blob/main/spec/src/main/asciidoc/repository.asciidoc) adds:

[quote]
A superinterface of a repository interface is not considered to have a well-defined primary entity type, and
so--unless the superinterface is one of the built-in generic repository supertypes--each of its operations must have a
signature which explicitly determines the entity type it acts on, according to the rules given above.

`_Repository` is such a superinterface, so it declares no primary entity type for `HeadRepository`;
`CrudRepository<Head, Long>`, named on `HeadRepository` itself, does. hibernate-processor already follows that rule, and
its error message uses its words. So this is not a hibernate-processor bug but the 1.1 rule, applied early.

== How hibernate-processor looks for it

hibernate-processor, which generates the repositories at compile time, looks for the primary entity type in
`org.hibernate.processor.annotation.AnnotationMetaEntity#primaryEntity(javax.lang.model.element.TypeElement)`
(https://github.com/hibernate/hibernate-orm/blob/main/tooling/metamodel-generator/src/main/java/org/hibernate/processor/annotation/AnnotationMetaEntity.java):

. Among the superinterfaces of `HeadRepository`, it finds `_Repository<Head, Long>`. That is not `DataRepository`,
  `BasicRepository`, or `CrudRepository`, so it recurses.
. It recurses on the declaration `_Repository<T, U>`, not on the use `_Repository<Head, Long>`, so `T = Head` is lost.
. Inside `_Repository`, it finds `BasicRepository<T, U>`. Its first type argument is the type variable `T`, not a
  declared type, so nothing is found.

When the recursion finds nothing, the lookup goes on to the next superinterface.

== Workaround

Each repository also names `CrudRepository` directly, with its own types:

[source,java]
----
@Repository
public interface HeadRepository
        extends _Repository<Head, Long>,
                CrudRepository<Head, Long> {
----

`CrudRepository<Head, Long>` has `Head` as its first type argument, and the methods inherited through `_Repository`
resolve from there.

== Notes

* Spring Data has no such rule and resolves the generics at run time, so `heads-of-governments-spring-data` needs only
  `_Repository<Head, Long>`.
* The `@Find` methods are not affected. As 1.1 requires of the operations of such a superinterface, their signatures
  determine the entity type; hibernate-processor reads each as a member of the repository, so a
  `@Find List<T> findAll(Order<T>)` declared in `_Repository` works as `List<Head>` for `HeadRepository` without
  `CrudRepository<Head, Long>`. (The module now declares `@Find List<E> findAll(Order<E>)` in each repository, with its own
  entity type, and `_Repository` declares no methods.)
* For the book: chapter 1's Jakarta Data section (`chapter01_90_data.asciidoc`) shows the repositories with the
  workaround in place.
