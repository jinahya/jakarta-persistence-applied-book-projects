= Projects exercises

Which of the exercises in each `<domain>-persistence` module the book shows, and which ones the `-spring-data` and
`-jakarta-data` modules answer.
The exercises themselves, every one of them, are stated in each `-persistence` module's `EXERCISES.asciidoc` and
registered, with their ids, in its `EXERCISES.yaml`; this file only picks from them.
See link:../PROJECTS_STRUCTURE.asciidoc[] for the modules.

== Rules

. *One per level, for the book.*
  For each section of a `-persistence` module (a table, a view, or `SCHEMA`) and each level (Basic, Intermediate,
  Advanced), one exercise is picked; a level with nothing to pick is skipped (rules 5 and 6).
  The book shows the Basic and the Intermediate pick of each section, and not the Advanced one (since 2026-10-24, to
  keep the book's size down as more projects come); the data modules answer all three (rule 3).
. *Tested in the `-persistence` module.*
  Every exercise is answered there, in SQL (`src/test/sql-exercises/<table>/0N_<level>.sql`) and in JPQL and with the Criteria API
  (`<Section>_Exercises_<NN>_<Level>_PersistenceIT.Exercise<N>Test`), so the book's picks are too.
. *The same picks, in each data module.*
  Each `-spring-data` and `-jakarta-data` module of the domain answers the book's picks as well, as repository methods
  with tests, and with what the platform adds: sorting and pagination.
  That is why the data modules exist.
. *One more per level, in each data module, not the same.*
  Each data module answers one more exercise of each section and level, besides the book's pick.
  The two data modules of a domain pick different ones, so between them they show three exercises per level.
. *Basic is plain.*
  Intermediate and Advanced methods take the platform's paging and sorting (rule 3).
  Basic methods do not: they keep a few methods of each data module plain, the way a repository is also written.
  The book's Basic pick, which both data modules share, returns a `List`; each data module's own Basic extra returns a
  `Stream`.
  The order is the exercise's own, written in the query.
  So a Basic exercise is picked only if it returns rows, a whole list of them bounded by its own filter: not one with a
  `LIMIT` (a top five is a page), and not one that gives a single value (a count is not a list).
  A grouped count, one row per group, is a list and qualifies.
  A section whose Basic exercises are all of the other kind has no Basic pick until one is added to its `-persistence`
  module.
. *Native SQL on its own list.*
  An exercise only native SQL can answer is flagged `native-only: true` in `EXERCISES.yaml`, and is never picked; a
  level whose exercises left to pick are all native-only is skipped.
  Instead, each data module answers every native-only exercise of its domain with a native query, and tests it; see
  <<native-only>>.
  Whether the book shows any of them is not decided.
. *Picks are stable.*
  A pick is not changed until a better case is found.
  A change is recorded under <<changes>>, with the date and the reason, and the book and the modules follow it.
  An id is never reused or renumbered; see the header of each `EXERCISES.yaml`.

A level a section does not have (no Advanced exercise, say) has no pick.

Throughout, JPQL and the Criteria API select entities, not their columns: where an exercise's SQL selects some columns
of a table (its key, a name, ...), the query selects the entity (`a`), grouped by it where it groups
(`SELECT a, COUNT(fa) ... GROUP BY a`), and the reader takes the columns from it.
What the SQL computes, a count, a sum, an average or another expression, stays a scalar beside the entity.
The SQL does the same with `alias.*`: where it would list a table's columns, it selects the row
(`SELECT a.*, COUNT(*) AS films ... GROUP BY a.actor_id`), and a native query keeps the exercise's SQL as it is.
A table with a binary column that does not print (`staff.picture`, `address.location`) is the exception: its select
lists every column but that one, with a comment saying why.

== Templates

=== The book

A Basic or Intermediate pick is a `==== 연습문제: <title>` subsection of its section's chapter, in Korean; the heading
carries no level, and the Advanced pick is not shown (rule 1).
It states the problem, then answers it in SQL, with the output of a run against the installed database, then in
Query Language and with the Criteria API.
Each block carries an `// AI:` line naming the source it was copied from and the exercise id; the id itself is not
rendered.
The exercises of a section that are not picked are left to the reader, who finds them in the module's
`EXERCISES.asciidoc`.

The data modules' answers are not shown in the book (since 2026-10-24; the chapters they had, 4 for `-spring-data`
and 5 for `-jakarta-data`, were removed at tag `pre-production-wip`): the book's Query Language and Criteria API carry
over to a `@Query` and a `Specification` almost unchanged, and the rest of what those chapters taught was the
frameworks' own rules.
The modules themselves remain the reference answers (rules 3 and 4).

=== `<domain>-persistence`

`EXERCISES.asciidoc` states the problem under `[[<ID>]]` / `==== <ID>: <title>`, with the SQL in a collapsible block.
`EXERCISES.asciidoc` and `EXERCISES.yaml` are in `src/test/sql-exercises`, and so is the SQL, a directory per section
and a file per level:

[%autowidth,cols="d,m",options="header"]
|===
| Section | File

| a table or a view | <table>/01_basic.sql +
<table>/02_intermediate.sql +
<table>/03_advanced.sql
| the whole schema | __/01_basic.sql +
__/02_intermediate.sql +
__/03_advanced.sql
|===

The number only orders the files. A directory is named after the file of `src/test/sql` it exercises: `<table>` for a
table or a view, `__` for the whole schema, and `_<Schema>` for one schema of a database with several.
A file holds its level's exercises in id order, each under a ruler that carries its id.
A level a section has no exercise for has no file.
`EXERCISES.yaml` registers the id, its section, level, title, the `.sql` file and the `test:` that answers it.
Nothing marks a pick here; this file does.

The tests are a class per section and level, `<Section>_Exercises_0N_<Level>_PersistenceIT` against a database the
module does not hold (MySQL in Docker), `..._PersistenceTest` against one it does (the SQLite file), with a
`@Nested class ExerciseNTest` per exercise in number order.
An exercise's cases are `__QueryLanguage` then `__CriteriaApi`, standard JPQL and Criteria API that every provider of
the module runs; a native-only one has a `nativeQuery` case instead.
Every `test:` in `EXERCISES.yaml` names a nested class that exists.

=== `<domain>-spring-data`

One method per exercise on the repository of the exercise's section.
Its javadoc names the exercise id and the sort the exercise asks for.

* Basic: the book's pick returns a `List`, the module's own extra a `Stream`; no `Pageable`, no `Sort`, the order in
  the query (a derived `...OrderBy...` method, or a `@Query`).
* Intermediate and Advanced: the method takes a `Pageable` and returns a `Page`, so the `LIMIT` of the exercise is the
  page's size: a `default` method building a `Specification` for an exercise that lists rows, a `@Query` with a count
  query for one that groups and counts.
  The order of the exercise stays in the query (since 2026-10-24, a caller should not have to know a select alias to
  get the exercise's answer; `SAKILA_ACTOR_I_02` is converted, the other Intermediate picks are to follow, see
  <<open>>); a sort of the pageable comes after it.
* Native-only: a `@Query(nativeQuery = true)` method, the SQL as `EXERCISES.asciidoc` has it.
* A method whose rows are not entities, grouped or native, returns `jakarta.persistence.Tuple` (in a `List`,
  `Stream`, `Page` or alone), not an interface projection or a record: the caller reads each column by its alias, and
  a `Sort` names the same alias.

Each method has a `@Nested` test class in both the `_DataJpaTest` and the `_SpringBootIT` of the repository.
`ActorRepository` and its two tests are the reference.

In a repository the exercise methods come after the others, in id order: Basic, Intermediate, Advanced, and by number
within a level; a native-only method takes its place in the same order.
Its javadoc names the id and the role: the book's pick, the module's own extra, or native-only.
Each test class nests a `@Nested` class per method in the same order, and within it the cases go: what the method
returns, then its order, then its paging (Intermediate and Advanced), then its argument checks.

=== `<domain>-jakarta-data`

One method per exercise on the repository of the exercise's section, its javadoc naming the exercise id and the sort.

* Basic: the book's pick returns a `List`, the module's own extra a `Stream`; no `PageRequest`, no `Order`, the order
  in the query (`@OrderBy` on a `@Find`, or `ORDER BY` in a `@Query`).
* Intermediate and Advanced: the method takes a `PageRequest` and an `Order` (or `Sort`) and returns a `Page`, through
  `@Find` or `@Query`.
* Native-only: Jakarta Data's `@Query` takes JDQL alone, so the method carries Hibernate's `@SQL`
  (`org.hibernate.annotations.processing.SQL`) with the SQL as `EXERCISES.asciidoc` has it.
* A method whose rows are not entities, grouped or native, returns `jakarta.persistence.Tuple` (in a `List`,
  `Stream` or `Page`), not a record: the caller reads each column by its alias, so the query's aliases are the result's
  shape, and a native query's column types (MySQL's `TINYINT` as `Byte`, `SMALLINT` as `Short`) need no matching
  declaration, which keeps such methods testable on H2 too.

Each method is tested on both persistence units, `test` and `it`, in the repository's `_WeldTest` and
`_WeldIT`.

In a repository the exercise methods come after the others, in id order: Basic, Intermediate, Advanced, and by number
within a level; a native-only method takes its place in the same order.
Its javadoc names the id and the role: the book's pick, the module's own extra, or native-only.
Each test class nests a `@Nested` class per method in the same order, and within it the cases go: what the method
returns, then its order, then its paging (Intermediate and Advanced), then its argument checks.
