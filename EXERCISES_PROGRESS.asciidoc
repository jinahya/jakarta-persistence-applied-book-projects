AGENT INSTRUCTIONS (not rendered). Read them whenever the author mentions this file, exercises review, or asks to
continue. Any agent may run them; a run picks up where the last one stopped.

What this is: an everlasting review of the exercises of every -persistence project, one schema at a time. Each unit
gets a blind review by Codex and an independent review by Claude; the two are discussed, the conclusions applied.
Nothing is missing that started it; it is kept going so the exercises keep getting better.

Rules
- One unit at a time, in the order of the queue below. A run starts at the first unit whose status is not `done`, and
  resumes a unit from the step its status names.
- Never run the SQL during Phase 1, and never tell Codex to. No database, no container, no docker. SQL is validated
  only in Phase 2, after every unit of Phase 1 is `done`.
- Ids are never reused. An exercise whose meaning changes is retired and added anew; a fix keeps the id only when the
  request stays the same question. A new exercise takes the next unused number of its section and tier, counting the
  retired ones.
- A retired exercise stays in EXERCISES.yaml with `retired: true`; it leaves EXERCISES.asciidoc, its .sql file and its
  nested test class.
- Where an output would be, a new or changed exercise carries `NOT YET RUN` instead: in EXERCISES.asciidoc a line
  `// NOT YET RUN` where the `....` block goes; in the .sql file a line `-- NOT YET RUN` under the statement, in a module
  whose .sql files carry output. Phase 2 replaces each with a fresh run's output.
- Every live exercise has its nested class in src/test/java-exercises: `@DisplayName("<ID>: <title>") @Nested class
  <ID>_Test {}`, in the `<Dir>_Exercises_<NN>_<Level>_Persistence{IT|Test}` class of its .sql file (projects/CLAUDE.md).
  A nested class that has tests stays as it is; a missing one is added empty.
- Keep the module's own conventions (its CLAUDE.md, the header of its EXERCISES.yaml, projects/CLAUDE.md, and the
  paging rule of ../CLAUDE.md). Do not touch the book.
- Before a unit, check that no other session or loop is writing the same files (`git status`, recent mtimes).
- If Codex fails (token limit, error, timeout), record `codex: skipped (<why>)` for the unit, review it alone, and go on.
- Each unit ends with `./mvnw -o -q test-compile` in its project, a local commit in the affected submodule and in
  projects/ (on develop, never pushed), and its status `done`.

Steps of a unit (the status names the next step)
1. `pending` -> gather the inputs into exercises_progress/<UNIT>/: the unit's EXERCISES.asciidoc sections, its
   EXERCISES.yaml entries (retired ones too, for the numbering), and the schema's source DDL (see the queue).
2. `inputs` -> Codex, blind: run
     codex exec -s read-only --skip-git-repo-check -C exercises_progress/<UNIT> -o exercises_progress/<UNIT>/review-codex.md \
       "$(cat exercises_progress/CODEX_PROMPT.md)"
   with only the inputs in that directory. Status `codex`.
3. `codex` -> Claude reviews the same inputs before reading review-codex.md, into exercises_progress/<UNIT>/review-claude.md.
   Status `claude`.
4. `claude` -> discuss: read review-codex.md against review-claude.md; for each item decide agreed / rejected / merged, with a
   reason. Items the two disagree on go back to Codex once (exercises_progress/<UNIT>/review-codex-reply.md). The decisions go
   in this file, under the unit. Status `decided`.
5. `decided` -> apply the decisions to EXERCISES.asciidoc, EXERCISES.yaml and the .sql files, and the nested classes.
   test-compile, commit. Status `done`.

Phase 2, after every unit is `done`: one database at a time, start its container (`docker compose up -d` in the
project), run every statement whose output is `NOT YET RUN`, write the output in its place, fix a statement that fails,
then `docker compose down -v` and remove what it pulled if disk is short, before the next database. Never two at once.
