= Projects build

The Maven profiles, the shell scripts and the Docker Compose files of the submodules under `projects/`.
This is a standard, not a checklist: a submodule has only the profiles and scripts it needs, and those it has go by the
names, and do what, this file says.
See link:PROJECTS_STRUCTURE.asciidoc[] for the modules and link:PROJECTS_VERSIONS.asciidoc[] for what a generation
profile builds against.

== Maven profiles

[cols="3m,8,4",options="header"]
|===
| Profile | What it does | Where it applies

| failsafe
| Binds `maven-failsafe-plugin` (`integration-test`, `verify`), so `verify` runs the `*IT` classes.
Off by default: an integration test may need a database a plain build does not have.
| a module with integration tests

| jakarta-ee-<N>
| Builds against Jakarta EE `<N>`: its `jakarta.jakartaee-bom` and the provider versions of that generation, as
link:PROJECTS_VERSIONS.asciidoc[] sets them.
The current generation's is `activeByDefault`.
| a module on one provider, or none

| jakarta-ee-<N>-<provider>
| The same, on one persistence provider: `hibernate-orm` or `eclipselink`.
The current generation's `hibernate-orm` is `activeByDefault`.
| a module that runs on more than one provider
|===

A module with generation profiles has either `jakarta-ee-<N>` or `jakarta-ee-<N>-<provider>` ones, never both.
A new generation adds its profiles next to the old ones, and moves `activeByDefault` to them.
`_alignment.py` resolves a module once per such profile.

== Scripts

Every script sits at the root of its module, starts with `_`, runs from its own directory whatever the caller's, and
passes its arguments on to the command it runs:

[source,sh]
----
cd "$(dirname "$0")" || exit 1
exec ./mvnw <profiles> <goals> "$@"
----

=== Maven

`_mvn_<profile>_<goal>.sh`, where `<profile>` is the generation profile with `-` as `_`
(`jakarta_ee_11`, `jakarta_ee_11_hibernate_orm`), left out, with its `_`, for a module that has none.

[cols="4m,6m,6",options="header"]
|===
| Script | Runs | For

| _mvn_<profile>_test.sh
| ./mvnw -P<profile> clean test
| the unit tests

| _mvn_<profile>_verify.sh
| ./mvnw -Pfailsafe,<profile> clean verify
| the unit and the integration tests

| _mvn_<profile>_verify_notests.sh
| ./mvnw -Pfailsafe,<profile> clean verify -DskipTests -DskipITs
| the build alone
|===

A module with `jakarta-ee-<N>-<provider>` profiles has the three scripts once per provider.

=== Docker Compose

A database the integration tests need runs from a `compose.yaml` at the root of the module that owns it, with the
files it initialises the database from beside it (`docker-entrypoint-initdb.d/`).
`_compose.sh` brings it up from an empty data directory (`down -v`, then `up -d`), follows its log, and takes
it down again, with its data, on Ctrl-C.
It runs `docker compose`, or `docker-compose` where the plugin is missing.

Only the owning module has them.
Another module of the domain uses the owner's, from the sibling checkout:

[source,sh]
----
../mysql-sakila-persistence/_compose.sh
----

== Open

Where what is there does not follow the names above yet; as gathered on 2026-10-23.

* The provider scripts of `mysql-sakila-persistence` put the provider after the goal
  (`_mvn_jakarta_ee_11_test_hibernate_orm.sh`); the pattern above puts it in `<profile>`, before the goal
  (`_mvn_jakarta_ee_11_hibernate_orm_test.sh`). One of the two is to give way.
* `heads-of-governments-persistence`'s `_mvn_effective_poms.sh` runs `mvn`, not `./mvnw`, without the `cd`, and its
  name has a `.`; under the pattern above it would be `_mvn_<profile>_effective_pom.sh`.
